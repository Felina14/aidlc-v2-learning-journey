### Checks you asked for

- **Plan fidelity:** The delivered files match the plan layout. `milestones.ts`, `nudge.ts` and `certificate.ts` are new, the backend, `api.ts`, `state.ts`, `render.ts`, `app.ts`, `types.ts` and `goal.ts` are edited, and the stack route and tests are present. `main.ts` passes `getNudgeStorage: () => window.localStorage`, so dismissals persist in production. The plan checkboxes are not ticked (Minor).
- **BR coverage:** BR40 to BR45 each have an implementation and a test (see the traceability finding for BR45.1).
- **Milestones only after a confirmed mark:** `applyChange` computes the plan only on a confirmed `completed` result. The tests cover no banner on an unmark, on a failed mark, or on a plain load.
- **Shown-set logic:** `countsAsShown` counts a milestone as shown when it is in the set or below the highest in the set. New milestones join the shown set before any call. 200 answers are merged. The set is emptied and refilled in `enter`, `goHome` and `confirmDelete`. A late answer is dropped by the `journeyGen` check.
- **Quiet failures:** `recordMilestones` does nothing on any non-`saved` result. The banner stays and the shown set keeps the milestone for the visit. The retry is limited to network failures and timeouts through `callWithOneRetry`.
- **Certificate name:** The name is only read from the input and written with `textContent`. It is not in state, a request, storage or an announcement. `app.test.ts` checks fetch calls, session storage and nudge storage. No test checks log output or the live region for the name. The backend never receives it, and the handler log line carries only route, status and outcome.
- **Nudge boundaries:** `doneCount * 2 >= total` blocks a nudge at 3 of 6 and 3 of 5, and allows 2 of 5. Days are limited to 0 to 3 through `goalState`, and passed, none or complete states are excluded. Next stage is the lowest not done.
- **Dismissal storage cleanup:** Markers use one prefix and a goal-date and local-day key. Older days are removed on write. `clearAll` runs on delete, replace and "gone". Memory is the fallback when storage throws. A load does not clear them.
- **Blocked-word test strength:** The test covers all four days over next-stage and stages-to-go 1 to 6 and 99. It also covers page-rendered text, apostrophe normalisation, whole-word matching ("template", "later") and "only N day(s)". The weaknesses are minor (see above).
- **Conditional update and sorted answers:** `mark_milestone_shown` is one `update_item` with ADD, `lastActivityAt` and `expiresAt` moved, and the condition `attribute_exists(sessionId) AND expiresAt > :now`. It uses `ReturnValues="ALL_NEW"` so a repeat still returns the set, and `sort_milestones` fixes the order. A failed condition is NOT_FOUND and other errors are SAVE_FAILED. Moto tests and stubbed-client tests cover these.
- **Empty-set save:** `save` leaves out `milestonesShown`. A missing attribute, a set and an empty list all load as empty. A replacement journey starts with none.
- **Route and stack:** The handler route checks the session ID and the body, and ignores extra keys. The stack adds one `PUT` route on the existing integration. Tests assert unchanged table actions, `PUT` allowed on `/api/*`, and no new alarm or filter.

### Summary

The unit is implementable and verified: the rules, the conditional update, the shown-set logic, the quiet failures and the certificate-name handling are all implemented as specified, and both suites pass. The one Major finding is that dismissing a banner loses keyboard focus, which breaks the focus rule in the interaction spec. The remaining findings are traceability and test-hygiene points. No Critical finding, and one Major (the limit for READY is two).
