> R-01 Reviewer note: completedStages is now a number set that is absent when empty (entities.md Journey > completedStages; rules.md BR11.1, BR12.2). Mark uses a set add on an absent attribute, which DynamoDB allows and which creates the set. Unmark uses a set delete, and removing the last number removes the attribute. The first unit's save (store.py writes completedStages as an empty list) must change to omit it, and the spec says so in its assumptions. The "not deployed" premise is stated, not verified, and the leftover legacy-list case ends as SAVE_FAILED by design. Acceptable.

> R-02 Reviewer note: One conditional update carries exists, expiresAt greater than now, and stageCount at least N, with stageCount stored by the save. A missing stageCount makes the comparison fail, which is classified as INVALID_REQUEST, and that is stated. Classification uses the record returned with the failed condition, so no second read is needed. Returning the old item on a failed condition is a documented DynamoDB option on UpdateItem and needs a recent boto3, which is a code-generation detail. NOT_FOUND is checked before INVALID_REQUEST, so there is no ordering conflict.

> R-03 Reviewer note: The pressed stage's panel stays open after an unmark. Its stated reading is consistent with the interaction spec: the unmarked stage is either the earliest not-complete stage, or "the stage that was open before" is the pressed one. The spec's other clause ("first stage not yet complete opens") only differs when the pressed stage is not the earliest, and the design flags this as an assumption for the gate. Failed, NOT_FOUND and INVALID_REQUEST reopen the pressed panel with focus on its button (BR10.4, BR13.1, BR13.3, BR13.7, state machine). Consistent.

> R-04 Reviewer note: BR13.7 and workflow step 13 add the INVALID_REQUEST outcome with a Reload button, and the state machine includes it. BR13.2 makes saves strictly one at a time, so a later optimistic change cannot be overwritten by an earlier answer's list. Traceability covers BR13.2 under AC3.1.3 and BR13.7 as a reverse N/A.

> R-05 Reviewer note: expiresAt is epoch seconds (entities.md, BR11.4). The store's own clock is used for both tests. The completion test (expiresAt greater than now) is the exact opposite of the load test (at or before now), as BR11.2 and BR12.1 state. Matches store.py, which uses int(expiresAt) <= int(now).

> R-06 Reviewer note: BR11.5 and workflow step 10 state that a timed-out write may have been saved, that "Try again" is the idempotent correction, and that a reload shows the stored truth. The 20-second worst case in BR13.1 (two 10-second waits) is consistent with the 10-second load wait and the one retry.

> R-07 Reviewer note: BR11.3 and entities.md CompletionChange fix the stage number form (ASCII digits, no sign, no leading zero, 1 to 6) and say extra body keys are ignored. The business scenarios include the "02", "+2" and "2.0" cases.
